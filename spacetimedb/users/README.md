# Separate public guest-profile registry

This module stores public prototype guest profiles in `guest_profile`. Anyone can read the profiles and call the insert-only `create_guest_profile` reducer without a database token. It validates IDs/names, permits harmless retries, and rejects attempts to change an existing profile. This implements the prototype's unverified name-only user picker; it is not private account authentication.

| Column         | Type                | Value                                                            |
| -------------- | ------------------- | ---------------------------------------------------------------- |
| `id`           | string, primary key | Generated by the backend: `guest-` followed by 32 hex characters |
| `household_id` | string              | Always `demo-home` for this prototype                            |
| `name`         | string              | Guest's trimmed, single-line display name, 1–50 characters       |

Profiles contain no passwords, session/API secrets, microphone recordings, images, or object-placement attribution. Display names are publicly readable. A legacy private `registry_owner` table and its initializer remain in the schema so upgrading the earlier private registry does not remove existing rows. That table is no longer required to authorize guest creation.

## 1. Publish or update your own users-only database

From the repository root:

```bash
cd "/Users/preejedi/Desktop/CalHacks_Kyuran_Alex_Pree"
npm run typecheck
npm run test:module
spacetime login
```

If you **already created a users-only database from this module**, replace `YOUR_USERS_DATABASE_ID` with the identity returned by that earlier publish:

```bash
spacetime publish --server maincloud --module-path spacetimedb/users --no-config --delete-data=never YOUR_USERS_DATABASE_ID
```

This updates that registry's guest table from private to public, retains its rows and private owner table, and enables public insert-only guest creation. Do not omit the target when updating an existing registry: omitting it creates another database. Keep `--delete-data=never`; if the CLI reports incompatible changes, resolve those instead of resetting data. Private-to-public visibility is supported by [automatic migrations](https://spacetimedb.com/docs/databases/automatic-migrations/).

If you **have not created a users-only database yet**, omit the target to create a new one:

```bash
spacetime publish --server maincloud --module-path spacetimedb/users --no-config --delete-data=never
```

Save the new identity returned by publish. Publishing this module creates its tables automatically; no manual `CREATE TABLE`, owner token in `.env`, or `create_household` call is needed.

## 2. Configure the root `.env` (the earlier “step 3”)

Edit these settings in the existing repository-root `.env`, preserving Meta/Gemini/storage settings:

```dotenv
GUEST_PROFILE_STORE=spacetimedb
SPACETIMEDB_PROFILE_ACCESS=public
SPACETIMEDB_PROFILE_TABLE=guest_profile
SPACETIMEDB_URL=https://maincloud.spacetimedb.com
SPACETIMEDB_DATABASE=YOUR_USERS_DATABASE_ID
SPACETIMEDB_SERVER_TOKEN=
```

Replace `YOUR_USERS_DATABASE_ID` with your own registry's actual ID or name, not the dashboard URL or your friend's database ID. Leave `SPACETIMEDB_SERVER_TOKEN` empty. Public mode deliberately sends no database Authorization header. Setting public mode does not itself change table visibility: the updated module must be published first. Anonymous public SQL/reducer access is documented in the [HTTP authorization guide](https://spacetimedb.com/docs/http/authorization/).

The app still uses its normal backend guest sessions. Only selectable guest profiles use this registry; object/image storage and session hashes retain their existing configuration. Temporary local profiles are not automatically imported into this database.

6. Inspect `guest_profile` in your users-only database dashboard. Alternatively, query without logging in:

   ```bash
   spacetime sql --server maincloud --no-config --anonymous YOUR_USERS_DATABASE_ID 'SELECT id, household_id, name FROM guest_profile'
   ```

No manual row insertion is needed. The UI's new-user form creates records through FastAPI and the reducer. Switching to an existing user selects their profile rather than inserting another row. Entering the same name again creates a distinct ID.

If setup fails, check the database ID, whether the updated module was published, and whether you restarted the API. A missing table or denied reducer produces a visible error rather than an empty temporary directory. For temporary testing without the registry, set `GUEST_PROFILE_STORE=local`; selectable users then reset on API restart.

## Vultr

Set the same five registry variables on the Vultr backend. No SpacetimeDB runtime token or CLI installation is needed for this public registry. Keep Meta/Gemini keys and other services' credentials in backend secrets. Vultr's object/image/session persistence remains a separate integration.

## Verification

`npm run typecheck` and `npm run test:module` cover schema composition, visitor insertion, validation, retry behavior, and prevention of existing-profile changes. Backend tests cover public HTTP access without an Authorization header and profile reselection after API restart. These local checks do not verify a hosted publication; complete the UI test after publishing to your own registry.
